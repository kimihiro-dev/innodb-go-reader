## 第一阶段：从简单 InnoDB 表空间完整还原行数据（已完成）

日期：2026-09-09。状态：用户已确认，第一阶段已完成。本文保留原计划的建议措辞，交付与验证见 `format/README.md` 和 `TODO.md`。

### 1. 问题与目标

问题：如何用 Go 从真实 `.ibd` 快照中找到记录、解释记录布局并还原每个用户列，同时让读者能够用实际字节复核整个过程？

首个里程碑：一张受明确约束的简单表，从生成数据、取得稳定快照、解析文件到对照 SQL 查询结果，形成可重复的完整闭环。

“完整”指这张受支持表中的全部行、全部用户列均正确恢复；同时保留记录头和系统字段的原始信息，解释其含义。它不表示第一步就支持任意 `.ibd`、所有类型或事务可见性恢复。

### 2. 建议输入范围

| 项目 | 第一步建议 |
|---|---|
| 版本 | 本地已核实的 MySQL 8.0.45 |
| 表空间 | 独立、非压缩、非加密 `.ibd`；16 KiB 页 |
| 表 | 新建的专用测试表；无 ALTER/INSTANT 历史、无并发写入，夹具只做插入 |
| 行格式 | DYNAMIC；本步数据全部存于页内 |
| 索引 | 显式单列 INT 主键，无二级索引；聚簇根页同时为叶子页 |
| 用户列 | 有符号 INT，以及 UTF-8 的短 VARCHAR；覆盖可空列 |
| 元数据 | 显式提供简单 schema 和已核对的聚簇根页号；不把根页写死为 3 或 4 |
| 读取模式 | Go 解析器只读离线快照，不连接 MySQL 获取行数据 |

“单叶子页”不是说整个 `.ibd` 只有一个页。文件还包含表空间管理、SDI 等页面；本步按已验证的入口页读取用户记录，不把所有 INDEX 页拼起来当作表数据。

元数据是独立输入：只给字节流无法在当前阶段可靠判断每列类型。首步不引入 SQL parser 或 SDI schema 恢复，避免混合多个学习主题。此取舍仅缩小第一步，不作为最终 API 限制。

### 3. 贯穿示例（待实施时生成）

```sql
CREATE TABLE lesson_rows (
    id INT NOT NULL,
    score INT NULL,
    name VARCHAR(32) NULL,
    PRIMARY KEY (id)
) ENGINE=InnoDB ROW_FORMAT=DYNAMIC DEFAULT CHARSET=utf8mb4;

INSERT INTO lesson_rows (id, score, name) VALUES
    (7, 0, ''),
    (-3, 42, 'InnoDB'),
    (12, -5, '你好'),
    (2, NULL, NULL);
```

使用乱序主键插入，让读者观察记录链接顺序与物理存放位置的区别。示例同时展示正负整数、0、空字符串、NULL、多字节 UTF-8。VARCHAR(32) 刻意控制长度，本步不覆盖长字段的两字节长度和页外值。

测试还应包含空表、单行表、INT 最小/最大值、最长允许字符串、NULL 与空值的组合；不把固定的四条示例数据硬编码为解析规则。

### 4. 分步实现与验证

1. **建立可重复的数据夹具** → verify：保存生成 SQL、实际版本与表属性、索引根页、稳定快照、SQL 基准结果、文件哈希，后续无需运行 MySQL 也能执行解析测试。
2. **从文件定位用户数据页** → verify：文件偏移、完整页长度、FIL 头、页类型、space/index ID、INDEX 层级和已记录根页相符；确认根页是叶子页。
3. **沿页内记录链遍历** → verify：理解 infimum/supremum、记录头、next-record 偏移、记录数与目录槽；每个普通记录恰好访问一次，正确终止，检测越界与循环。
4. **还原各列与记录元信息** → verify：按 schema 读取 NULL 位图、变长长度、主键、系统字段、其他列；恢复 INT 符号及字符串字节，保留 DB_TRX_ID/DB_ROLL_PTR 原始信息但不做 undo 追溯。
5. **对照查询结果并完成文档** → verify：所有行所有列与同一稳定数据状态下的 `SELECT id, score, name ... ORDER BY id` 完全一致；测试可复跑，文档中字节来自最终夹具。

页目录和页头中暂未用于遍历的字段可以解释和保留；本步不实现目录二分查找、空间统计或热力图。基本读取边界检查直接服务于记录解码；完整校验算法支持矩阵不扩张本步范围。

支持范围之外的情况应明确返回不支持或输入错误，不能伪装为空表或成功结果。实现需区分可由页头/记录标志检测的限制与必须由夹具生成过程和输入元数据保证的前提；本步不能宣称自动识别所有不兼容表。

### 5. 验收标准

- 不依赖 MySQL 服务运行，Go 可以从交付的 `.ibd` 与元数据输入还原行。
- 正确还原测试表中全部用户列；NULL、空字符串、0 不混淆，UTF-8 不按字符数误取字节。
- 正确处理空表/单行/多行与乱序插入；不将 infimum/supremum 当作用户数据。
- 不依赖用户记录恰好位于某个固定偏移；由结构和指针定位。
- 截断页、无效偏移、记录链循环和意外非叶子入口有明确错误，无越界 panic 或无限循环。
- 系统字段标注“元信息”，不承诺快照可见性或删除恢复。
- 每步讲解文档随实现交付，读者能选择一条记录，从文件偏移逐字节算回 SQL 中的值。

1. 当前第一步：单个聚簇叶子页上的完整行还原。
2. 多页、多层聚簇索引的完整表扫描；页分裂后仍不丢行、不重复。

4. 逐步补充元数据自动发现、MySQL 8.0 LOB 和 INSTANT 等能力；具体先后由目标表和支持矩阵决定。

### 8. 技术方案与备选方案

- 标准库调查沿用 `REFERENCE_ANALYSIS.md` 第 8 节：`os.File.ReadAt`/`io.ReaderAt` 和 `encoding/binary` 可完成底层读取，标准库无现成 InnoDB 记录解码器。当前无 Go 依赖。
- 建议首步仅使用标准库，测试使用 `testing`，暂不建立存储插件、缓存框架或完整 CLI。
- 显式 schema/根页输入优于首步实现 DDL/SDI 全链路：能直接聚焦字节到列值，但需在文档中公开这一依赖。
- 单叶子页优于首步完整 B+ 树：先证明记录解码正确，下步只增加树与页间遍历；不能将首步结果宣传为任意表扫描器。
- 仅固定长度整数更小，但不覆盖 NULL 与变长布局；加入短 VARCHAR 能在可控范围内建立更有代表性的数据还原闭环。

参考阅读：[MySQL 索引章节](https://dev.mysql.com/doc/refman/8.0/en/innodb-indexes.html)、[MySQL 行格式](https://dev.mysql.com/doc/refman/8.0/en/innodb-row-format.html)。具体字段偏移与位编码在实施各章前继续对照 MySQL 8.0.45 对应源码核实，不以通用手册替代版本级验证。

## 第二阶段：多页、多层聚簇索引整表扫描（已完成）

用户已批准，已完成。交付说明见 format/06-index-tree.md 至 format/08-tree-scan.md。

问题：从显式根页出发，找到分散在聚簇索引树中的全部行，并解释非叶子记录如何导航。

范围沿用 MySQL 8.0.45、16 KiB、DYNAMIC、独立非压缩非加密表空间、INT 主键、短 VARCHAR/NULL 和可信显式 schema；支持插入和页分裂产生的布局，不增加 DELETE/INSTANT、LOB、SDI 或其他类型。

方案：复用逐页记录链与叶子字段解码；非叶子记录解码 INT 键及四字节子页号。按键顺序深度优先遍历整棵树，使用显式栈而不是不受控递归；检查页归属、层级、重复访问、父子键范围、同层双向页链和全局主键顺序。保留 Read 的成功时完整结果/错误时不返回部分结果契约。

未采用：扫描文件中所有 INDEX 页拼接，原因是可能混入其他索引/残留页面。未采用：只沿叶子链扫描，原因是本阶段还需验证和讲解内部树结构。未采用：并发读取和缓存框架，原因是正确性优先且标准库 ReaderAt 已足够。

验收：

1. 原单页夹具全部通过。
2. 新增顺序、乱序插入的跨页表，以及真实根 level>=2 的三层树；逐行逐列与稳定导出期间的 SQL 基准一致。
3. 错误子页号、跨索引/表空间、层级不符、重复子页/循环、键范围冲突、兄弟链异常均报错。
4. 每条行包含页号，返回页和非叶子记录信息供手册追踪；不输出树导航记录为用户行。
5. 新增第 06–08 章：树组织、非叶子记录逐字节解码、整树遍历与复现。真实字节必须来自固定夹具。

测试资产可用 gzip 无损保存较大的 .ibd 与 SQL 预期；Go 解码器仍接受解压后的 ReaderAt，不把 gzip 加入 InnoDB 格式。

## 第三阶段：整数类型解析（已完成）

问题：现有 INT 限制使普通整数列及其他整数主键无法完整还原。
用户已批准整数扩展阶段。沿用 MySQL 8.0.45、16 KiB、DYNAMIC、显式 schema、单列主键、短 VARCHAR 和插入快照限制。

### 范围与约定

支持 TINYINT/SMALLINT/MEDIUMINT/INT/BIGINT，各自有符号或无符号。Column 新增 unsigned 布尔值，默认 false；VARCHAR 不接受 unsigned。
返回值依次为 int8/int16/int32/int32/int64；无符号为 uint8/uint16/uint32/uint32/uint64。旧 INT 返回类型不变。NodePointer.Key 改为 any，遵循同一类型表。
JSON 保持整数数字形式，Go encoding/json 精确输出；消费端须用 UseNumber 或等效精确整数解析，不得经 float64 中转。
内部排序映射为 uint64 有序值；上界显式标记是否存在，不用最大整数加一表示无穷。

### 备选方案

- 不统一转换 int64：不能容纳 BIGINT UNSIGNED 全范围。
- 不引入大整数依赖：固定宽度最多 64 位，标准库与原生整数足够。
- 不将所有数值转字符串：破坏现有输出约定；保留整数 JSON 并说明消费要求。
- 不同时扩展长 VARCHAR/LOB：单独阶段解释变长长度和页外存储。

### 实施与验收

1. 定义类型宽度、符号及返回约定；验证 schema 拒绝不支持组合。
2. 贯通普通列、主键、内部节点、页内排序和父子范围；验证 64 位极值无溢出。
3. 真实 MySQL 夹具覆盖十种主键组合、边界/NULL/混合列、跨页树；逐行逐列对照 SQL，JSON 以 UseNumber 检查。
4. 保留全部旧夹具回归；补充截断、排序及越界损坏测试，运行 test/race/vet/fuzz 与官方页校验。
5. 手册新增整数编码和整树验证章节，包含真实十六进制、宽度偏移、NULL、类型矩阵和复现方法。

### 审阅时需要选择的范围

本轮是候选路线图，不要求先回答这些问题才能阅读；相应实现开始前再收敛：

1. 首版是否聚焦 MySQL 8.0.45、16 KiB、非压缩非加密独立表空间？建议先保持，其余进入兼容分支。
2. 是否有实际含 GEOMETRY、分区、特殊字符集/排序规则的表？这决定22、23、25、38的优先级和具体矩阵。
3. 目标首先是稳定快照中的当前存储值，还是包含历史事务与故障恢复？建议前者为主线，E11–E13单独评估输入和工作量。
4. 首版是否需要虚拟列求值、完整 DDL/SQL 输入或 SQL dump？建议先完成物理值与 SDI 自动读取，再按需要增加E1/E10/E15。
5. 页面可视化是否纳入首版？建议先完成36的结构化分析，39可独立交付。

路线图列出目前已识别的功能域，不能保证涵盖所有未来发现的 MySQL 版本细节。后续新增遗漏项直接维护此清单；执行某阶段前确定其支持矩阵，完成后再将状态改为已实现。
