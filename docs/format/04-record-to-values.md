# 04. 从记录到列值

学习目标：对一条真实记录从头到尾解码，并理解 NULL、变长长度、有符号整数、UTF-8 和系统字段。前置知识：[第 03 章](03-page-to-record.md) 的 origin 和记录头。

<a id="1-先确定物理字段顺序"></a>

## 先确定物理字段顺序

本阶段有一个非空 INT 主键。聚簇叶子记录的数据部分依次为：

```text
主键 INT（4） → DB_TRX_ID（6） → DB_ROLL_PTR（7） → 其他用户列
```

其余用户列按原声明顺序处理。主键即使声明在 SQL 列列表最后，物理记录中仍先存主键；返回值则恢复为 `Schema.Columns` 的 SQL 列顺序。`null_bitmap_rows` 把 id 声明在最后，专门验证这一点。

这不是适用于全部 InnoDB schema 的通用公式：复合键、隐藏主键、虚拟列、INSTANT 历史等需要进一步处理；当前 `schema.go/validate` 与输入契约限制了范围。

<a id="2-完整解码-id3-这一行"></a>

## 完整解码 id=−3 这一行

来自 `lesson_rows.ibd`，页号 4，origin=155。整个记录 `[148,182)` 为 34 字节。下面“文件偏移”均由 65536 加页内偏移得到：

| 页内区间 | 文件偏移起点 | 实际字节 | 含义 |
|---|---:|---|---|
| `[148,149)` | 65684 | `06` | name 的字节长度 6 |
| `[149,150)` | 65685 | `00` | score、name 均非 NULL |
| `[150,155)` | 65686 | `00 00 18 00 43` | 固定记录头 |
| `[155,159)` | 65691 | `7f ff ff fd` | id，解码为 −3 |
| `[159,165)` | 65695 | `00 00 00 00 63 58` | DB_TRX_ID 原始 6 字节 |
| `[165,172)` | 65701 | `81 00 00 00 94 01 1d` | DB_ROLL_PTR 原始 7 字节 |
| `[172,176)` | 65708 | `80 00 00 2a` | score，解码为 42 |
| `[176,182)` | 65712 | `49 6e 6e 6f 44 42` | UTF-8/ASCII 字符串 InnoDB |

组合结果：`[-3,42,"InnoDB"]`。`Record` 还保存原始 Header、Transaction、RollPointer 与起止偏移，用户列值中不混入这些系统字段。

<a id="3-有符号-int-为什么不是直接大端读取"></a>

## 有符号 INT 为什么不是直接大端读取

InnoDB 对有符号整数的存储会翻转最高位。恢复当前四字节 INT 时：

```text
bits = 大端无符号 32 位数
value = int32(bits XOR 0x80000000)
```

| 存储字节 | XOR 后的位模式 | int32 结果 |
|---|---|---:|
| `7f ff ff fd` | `ff ff ff fd` | −3 |
| `80 00 00 2a` | `00 00 00 2a` | 42 |
| `80 00 00 00` | `00 00 00 00` | 0 |
| `00 00 00 00` | `80 00 00 00` | −2147483648 |
| `ff ff ff ff` | `7f ff ff ff` | 2147483647 |

最后两行在 `boundary_rows` 的真实 INT 极值测试中验证。这种编码使有符号整数的存储字节顺序更适合排序；不要将它套用于 unsigned INT、浮点数或事务 ID。

代码对应：`decodeRecord` 的主键和 INT 分支。格式依据：MySQL 8.0.45 [mach0data.ic](https://github.com/mysql/mysql-server/blob/mysql-8.0.45/storage/innobase/include/mach0data.ic) 中 `mach_read_int_type`。

<a id="4-null-位图按可空列编号"></a>

## NULL 位图按“可空列”编号

主案例只有 score、name 可空，所以需要 `ceil(2/8)=1` 字节。id 不是可空列，不消耗位。

读取时从 origin−6 的字节开始：最低位给第一个可空列 score，次低位给 name。置 1 表示 NULL。

| 位图 | score | name |
|---|---|---|
| `00` | 非 NULL | 非 NULL |
| `01` | NULL | 非 NULL |
| `02` | 非 NULL | NULL |
| `03` | NULL | NULL |

id=2 的 origin=222，其 `[216,222)` 为：

```text
03 | 00 00 28 ff a1
NULL 位图 | 固定记录头
```

name 为 NULL，因此没有它的长度字节。score 与 name 在数据部分均不占字节：数据只有主键 4 字节和系统字段 13 字节。整条记录为 `1+5+4+13=23` 字节，而不是给 score 填四个零再给 name 填空串。

结果是 `[2,null,null]`，不是 `[2,0,""]`。

<a id="5-超过八个可空列"></a>

## 超过八个可空列

`null_bitmap_rows` 有 n0..n8 和 name 共 10 个可空列，以及最后声明的非空 id。位图需要两个字节。id=2 的 origin=128：

```text
页内 121: 01     对应可空列 8..9 的位
页内 122: 55     对应可空列 0..7 的位
页内 123..127: 固定记录头
页内 128: origin，先存 id
```

阅读位图的顺序是从靠近记录头的字节向低地址移动。`0x55` 的位 0、2、4、6 为 1，所以 n0、n2、n4、n6 为 NULL；`0x01` 的位 0 为 1，所以 n8 为 NULL。name 对应后一个字节的位 1，为 0，因此有值“九列”。

算法为：第 k 个可空列使用 `b[origin−6−k/8]` 的 `k%8` 位。这里按索引记录中的可空字段顺序编号；在当前单个非空 INT 主键限制下，它与声明顺序中的可空列一致。

<a id="6-变长长度区也从后向前读取"></a>

## 变长长度区也从后向前读取

先确定 NULL 位图用了几字节，再把长度读取指针放到位图前面。按字段顺序，为每个非 NULL 的 VARCHAR 消耗长度字节；NULL 的 VARCHAR 不消耗。

在当前限制 `utf8mb4 VARCHAR(1..63)` 下，最大字节数不超过 252，每个长度只需要一字节。长度是字节数，不是字符数；长度 0 表示非 NULL 空字符串。

主案例 id=7 的 `[120,122)` 为 `00 00`：第一个 00 是 name 的长度，第二个 00 是 NULL 位图。因此 score=0、name="" 均是实际值。

`variable_rows` 有两个 VARCHAR。id=3 的 origin=128，元信息 `[120,123)`：

```text
03 fc 00
│  │  └─ NULL 位图：两个字符串都非 NULL
│  └──── 第一个 VARCHAR 长度：0xfc = 252 字节
└─────── 第二个 VARCHAR 长度：3 字节
```

读长度时先读靠近位图的 fc，再向前读 03；字段数据仍从 origin 往高地址依次读取。

这里第一个字符串是 63 个 😀，每个 4 字节，总计 252 字节。**fc 的最高位为 1，仍然是合法的一字节长度。**是否使用两字节长度首先取决于列的最大字节长度，不能只看当前长度字节的最高位。长 VARCHAR 与页外指针格式留到后续章节，当前通过 schema 限制避开。

<a id="7-中文为什么按六个字节取"></a>

## 中文为什么按六个字节取

id=12 的 name 为“你好”，实际字节 `[210,216)`：

```text
e4 bd a0 | e5 a5 bd
   你    |    好
```

长度字节为 06，因此必须取六字节，再按 UTF-8 解释成两个 Unicode 字符。若只取“两个字节”，会截断第一个字符。

Go 实现先用长度切出字节，再检查 `utf8.Valid` 和字符数是否超过 schema 的 MaxChars，然后转成 string。不支持的编码不会被替换字符悄悄掩盖。

<a id="8-系统字段说明了什么又没有说明什么"></a>

## 系统字段说明了什么，又没有说明什么

DB_TRX_ID 是记录的事务相关标识；DB_ROLL_PTR 与 undo 版本信息有关。当前保留固定 6/7 字节，不把回滚指针当作另一个 .ibd 页号直接跳转。

主案例中事务字节可按大端看作 `0x6358=25432`，但它不是行数、Unix 时间或数据版本的完整可见性判定。没有 ReadView 和 undo 遍历，读取物理记录不能自动等同于某个事务的一致性 SELECT。

本阶段样本来自无并发写入的稳定导出，并与该状态的 SQL 结果对照。删除标志记录被明确拒绝，而不是擅自恢复或忽略。

<a id="9-自己核对整条记录"></a>

## 自己核对整条记录

```sh
python3 - <<'PY'
from pathlib import Path
b = Path('testdata/mysql8045/lesson_rows.ibd').read_bytes()
raw = b[65536+148:65536+182]
print(raw.hex(' '))
print('length =', len(raw))
PY
```

结果应为 34 字节，与第 2 节逐段对应。之后运行项目示例，确认同一条记录还原成 `[-3,42,"InnoDB"]`。
