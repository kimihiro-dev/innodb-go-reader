# 09. 从整数物理字节到完整列值

本章扩展第 04 章：读懂五种整数、有符号与无符号的差别，并能从交付文件手工还原一条包含全部整数类型的记录。记录头、NULL 位图和主键优先布局沿用前文。

<a id="1-支持矩阵与可信元数据"></a>

## 支持矩阵与可信元数据

| SQL 类型 | 字节数 | 有符号范围 | 无符号范围 | Go 有符号 / 无符号返回类型 |
|---|---:|---|---|---|
| TINYINT | 1 | −128 … 127 | 0 … 255 | int8 / uint8 |
| SMALLINT | 2 | −32768 … 32767 | 0 … 65535 | int16 / uint16 |
| MEDIUMINT | 3 | −8388608 … 8388607 | 0 … 16777215 | int32 / uint32 |
| INT | 4 | −2147483648 … 2147483647 | 0 … 4294967295 | int32 / uint32 |
| BIGINT | 8 | −9223372036854775808 … 9223372036854775807 | 0 … 18446744073709551615 | int64 / uint64 |

普通列可为 NULL，单列主键必须非 NULL。MEDIUMINT 的物理宽度是 3 字节，返回 int32 并不意味着在文件里读取 4 字节。

schema 的类型名仍用大写，符号性通过独立字段表达，例如：

```json
{"name":"id","type":"BIGINT","unsigned":true,"nullable":false,"max_chars":0}
```

省略 unsigned 等同 false。整数不接受非零 max_chars；VARCHAR 不接受 unsigned。不接受 `type: "BIGINT UNSIGNED"` 这种 SQL 片段，元数据不是 DDL 解析器。

不能仅凭字节推断符号。8 字节 `80 00 00 00 00 00 00 00`，在有符号 BIGINT 中代表零，在无符号 BIGINT 中代表 9223372036854775808。必须由可信 schema 提供类型。当前仍不自动解析 SDI，也无法发现任意错误 schema。

<a id="2-大端符号翻转与符号扩展"></a>

## 大端、符号翻转与符号扩展

依据 MySQL mysql-8.0.45 的 [mach0data.ic](https://github.com/mysql/mysql-server/blob/mysql-8.0.45/storage/innobase/include/mach0data.ic) 中 `mach_read_int_type`（该标签第 712 行起），整数以高位字节在前保存；有符号整数的最高位被翻转。

无符号值直接按大端累积：每读一个字节，现有结果左移 8 位，再合入该字节。有符号值还需要恢复最高位，并按原始宽度进行符号扩展。

以下是算法示意，不是额外夹具截取：

| SQL TINYINT | 补码 | 文件字节 | 解码 |
|---:|---|---|---|
| −128 | 80 | 00 | 翻转得到 80，按 8 位有符号数解释 |
| −1 | ff | 7f | 翻转得到 ff，符号扩展后是 −1 |
| 0 | 00 | 80 | 翻转得到 00 |
| 127 | 7f | ff | 翻转得到 7f |

文件字节从 00 到 ff 的顺序，正好对应从最小负数到最大正数的顺序。符号翻转保留了整数的数值排序。

MEDIUMINT 的负数尤其容易出错：文件 `7f ff ff` 恢复最高位后为 `ff ff ff`，表示 24 位的 −1；若直接转换为 int32 而不符号扩展，会得到 16777215。

`integer.go` 的 `decodeInteger` 先用 uint64 累积，再翻转第 `bits−1` 位，最后用有符号右移完成符号扩展。8 字节类型也走同一流程，无需对最大值加一。

<a id="3-真实记录主键在声明中间物理上仍在最前"></a>

## 真实记录：主键在声明中间，物理上仍在最前

本阶段每张表都有十个可空整数列、一个非空整数主键和一个可空 VARCHAR(63)。schema 声明顺序是：

```text
 tinyint_s, tinyint_u, smallint_s, smallint_u, mediumint_s,
 id,
 mediumint_u, int_s, int_u, bigint_s, bigint_u, text
```

交付 `testdata/integers/bigint_unsigned.ibd.gz`，先解压才能计算物理偏移。本节来自主键 9223372036854775808 的真实行：页 10，Start=4642，origin=4650，End=4959。origin 对应文件偏移 `10×16384+4650=168490`。

```text
页内 4642                                                    4959
  [长度1][NULL位图2][头5] [主键8][事务6][回滚7][其他整数36][文本252]
                          ↑ origin=4650
```

以下为该记录完整的字段分段；文本按重复次数缩写，未省略任何其他字段：

| 页内偏移 | 长度 | 实际字节 | 含义 |
|---:|---:|---|---|
| 4642 | 1 | fc | 文本长 252 字节 |
| 4643 | 2 | 00 00 | 11 个可空列均非 NULL |
| 4645 | 5 | 00 00 98 01 3d | COMPACT 记录头 |
| 4650 | 8 | 80 00 00 00 00 00 00 00 | 无符号主键 9223372036854775808 |
| 4658 | 6 | 00 00 00 00 65 b2 | DB_TRX_ID 原始字节 |
| 4664 | 7 | 82 00 00 00 dc 01 10 | DB_ROLL_PTR 原始字节 |
| 4671 | 1 | 80 | tinyint_s = 0 |
| 4672 | 1 | 00 | tinyint_u = 0 |
| 4673 | 2 | 80 00 | smallint_s = 0 |
| 4675 | 2 | 00 00 | smallint_u = 0 |
| 4677 | 3 | 80 00 00 | mediumint_s = 0 |
| 4680 | 3 | 00 00 00 | mediumint_u = 0 |
| 4683 | 4 | 80 00 00 00 | int_s = 0 |
| 4687 | 4 | 00 00 00 00 | int_u = 0 |
| 4691 | 8 | 80 00 00 00 00 00 00 00 | bigint_s = 0 |
| 4699 | 8 | 00 00 00 00 00 00 00 00 | bigint_u = 0 |
| 4707 | 252 | f0 9f 98 80，重复 63 次 | 63 个 😀 |

逐步还原：从 origin 读主键 8 字节，再读系统字段 13 字节；之后按声明顺序遍历其他列，跳过主键位置，根据每种整数的宽度前进。十个整数一共占 `2×(1+2+3+4+8)=36` 字节。最终字符串结束位置为 `4650+8+13+36+252=4959`，与记录 End 一致。

`Record.Values` 最终仍按 SQL 声明顺序返回，id 放回第六项。事务字段只保留原始信息，不据此判断事务可见性。

<a id="4-null-不占整数数据字节"></a>

## NULL 不占整数数据字节

同一个文件中的最大无符号主键行位于页 17，Start=1733，origin=1741，End=2014，文件 origin 偏移 280269。它的十个普通整数列全部 NULL，text 非 NULL。

```text
fc | 03 ff | 00 00 40 f9 a3 |
ff ff ff ff ff ff ff ff |
00 00 00 00 65 ba | 82 00 00 00 e0 03 1f |
f0 9f 98 80 （重复 63 次）
```

位图从 origin−6 的 ff 开始读低位，再读取 origin−7 的 03，因此前十个位均为 1，第十一个位为 0。主键非空，不占 NULL 位。

此时主键后的 13 字节系统字段结束就直接进入文本，没有为十个 NULL 整数保留 36 字节。End 计算为 `1741+8+13+252=2014`。这一点同时验证了“NULL”和“整数零”具有不同物理布局。

<a id="5-再看真实的-3-字节主键"></a>

## 再看真实的 3 字节主键

`mediumint_signed.ibd.gz` 的主键 −8388608 位于页 5、origin=128，文件偏移 82048。主键字节为 `00 00 00`，恢复符号位得到 24 位 `80 00 00`，符号扩展后为 −8388608。

它的 DB_TRX_ID 从页内 131 开始，其他普通列从 144 开始。如果错误地按 4 字节读这个主键，后面的所有字段都会错位。真实行普通整数恰好都是各自最大值，物理部分共 36 个 ff 字节，文本从 180 开始，结束于 432。

<a id="6-api-和-json-精度"></a>

## API 和 JSON 精度

`Record.Values` 和 `NodePointer.Key` 使用上面的 Go 类型表。旧 INT 仍为 int32；NodePointer.Key 从固定 int32 改为 any，使用方应按 schema 做类型断言。

示例程序仍输出 JSON 数字。Go 的 encoding/json 可以精确写出 uint64 最大值；不能用 float64 接收后再转回整数：

```go
decoder := json.NewDecoder(input)
decoder.UseNumber()
var rows [][]any
err := decoder.Decode(&rows)
// json.Number 保留十进制原文。无符号 BIGINT 可用 strconv.ParseUint(text, 10, 64)。
```

JavaScript 等消费端同样需要保留大整数的 JSON 解析方式，普通 Number 不足以表示全部 BIGINT。解析器不把整数改成字符串，也不将溢出值填零。
