# 59 更新后的 LOB：引用、活动块与历史块

学习目标：从当前聚簇记录的20字节引用出发，解释为什么更新后不能再按“全部版本为1、全部事务相同、第一块在FIRST页”的规则读数据。

前置：[13 页外引用](13-lob-reference-and-pages.md)、[16 多页LOB索引](16-lob-index-pages.md)、[57 删除记录](57-delete-mark-layout.md)。本章扩展这些阶段的初始LOB限制；16KiB、非压缩非加密DYNAMIC、新格式LOB和单值16MiB限制保持。

## 1. 三种“版本”必须分开

- **页格式版本**：FIRST/INDEX/DATA页内偏移38的一字节，目前支持0。
- **LOB版本**：引用偏移8及FIRST页偏移40的四字节数字，初始为1；较大部分更新会递增。
- **块版本**：索引项偏移56，说明该块由哪次LOB版本产生。未修改的块可以比当前LOB版本旧。

事务ID另占六字节，它不是上述任何一种版本。小修改可能不增加LOB版本，却更新事务信息和数据字节。因此，版本为1不等于数据从未修改。

官方8.0.45源码 `storage/innobase/lob/lob0update.cc:109–161`：总二进制差异不超过100字节时走 `replace_inline`；否则递增LOB版本并替换块。阈值定义在 `storage/innobase/include/lob0lob.h:207–210`。这里的差异量不是SQL文本长度，也不是肉眼看到改变的字符数。

## 2. 引用标志不是值的类型

以下偏移均相对20字节引用起点，整数为大端。

| 偏移 | 长度 | 含义 |
|---|---:|---|
| 0 | 4 | space ID |
| 4 | 4 | FIRST页号 |
| 8 | 4 | 引用LOB版本 |
| 12 | 1中的高位 | 0x80 non-owner；0x40 inherited；0x20 being-modified |
| 12–15 | 4 | 除上述标志外，长度高位；本实现要求为0 |
| 16 | 4 | 完整页外字节数 |

0x80的含义是**不拥有释放权**，不能因常量名含OWNER就解释反了。0x40说明从旧行版本继承，影响回滚时谁能释放；两者本身不妨碍读当前值。0x20表示修改进行中，本项目拒绝读取。源码依据：`storage/innobase/include/lob0lob.h:119–136`。

真实 `values_inherited` 快照：主键从1改为11，新记录在聚簇页4、origin414，TEXT引用在页内431，文件偏移 `4×16384+431=65967`：

```text
0000029a 0000000a 00000001 40000000 00011170
```

逐段为space666、FIRST页10、版本1、inherited、长度70000。主键迁移不需要复制完整TEXT，当前行继承同一个LOB；旧键仍是delete-mark摘要，解析器不跟随旧记录的引用。

## 3. FIRST页和60字节索引项

FIRST页下面的数字是**页内偏移**，不是文件偏移。

| 页内偏移 | 长度 | 含义 |
|---|---:|---|
| 38 | 1 | 格式版本0 |
| 39 | 1 | flags；bit0=1表示不能继续部分更新，其他位暂拒绝 |
| 40 | 4 | 当前LOB版本 |
| 44 | 6 | 最后修改事务 |
| 50 | 4 | 最后修改undo序号 |
| 54 | 4 | FIRST本地数据长度 |
| 58 | 6 | FIRST数据创建事务 |
| 64 | 16 | 活动索引FLST：count4、first6、last6 |
| 80 | 16 | 空闲索引槽FLST |
| 96 | 600 | 十个60字节索引项 |
| 696 | 至页尾前8字节 | FIRST数据区 |

INDEX页从39开始容纳272个索引项。FIRST的FIL_NEXT（页内12）链接**分配的INDEX页**；链按新页在前组织，不能拿它当值的块顺序。

每个索引项的偏移均相对该项起点：

| 相对偏移 | 长度 | 含义 |
|---|---:|---|
| 0、6 | 各6 | 所属链的prev、next地址 |
| 12 | 16 | 此活动块的历史版本FLST |
| 28、34 | 各6 | 创建事务、修改事务 |
| 40、44 | 各4 | 创建undo序号、修改undo序号 |
| 48 | 4 | 数据页号 |
| 52 | 2 | 块长度；字段布局占4字节，54–55不是长度高位 |
| 56 | 4 | 块LOB版本 |

六字节地址为页号4+页内偏移2；空地址是 `ffffffff0000`。历史项自己的历史表头被置空，旧版本链由新的活动项统一持有。源码：`storage/innobase/include/lob0index.h:186–194`、`storage/innobase/lob/lob0index.cc:39–46`。

```text
当前记录引用 -> FIRST页
                ├─ 活动FLST -> 块A -> 块B -> 块C  （完整当前值顺序）
                │              └─ 历史FLST -> A旧2 -> A旧1
                └─ FIL_NEXT -> INDEX新页 -> INDEX旧页
                                   （活动/历史/空闲槽的分配池）
```

## 4. 从真实更新解码第一块

`documents_before` 的id1引用位于页4偏移145：

```text
0000029b 00000005 00000001 00000000 0000f979
```

space667、FIRST页5、版本1、63865字节。原第一项位于页5偏移96，数据也是页5，从696开始取15680字节。

`documents_small` 执行 `JSON_SET(j,'$.c[0]',2)` 后引用和块来源均不变。FIRST最后事务从 `000000009138` 变成 `00000000913b`，版本仍是1。这条样本直接说明不能凭LOB版本号判断是否需要undo。

`documents_large` 的同一引用只把版本改成2。活动表头首项成为 `(5,336)`，该60字节项为：

```text
ffffffff0000 00000005018c
00000001 000000050060 000000050060
00000000913e 00000000913e
00000000 00000000
00000020 3d40 0000 00000002
```

分步读取：

1. prev为空，next是页5偏移396。
2. 历史长度1，首尾均为页5偏移96，正是旧第一项。
3. 新块创建/修改事务均为0x913e。
4. 数据页号0x20=32，长度0x3d40=15680，块版本2。
5. 页32是DATA页，数据从页内49开始。因此文件读取区间为 `[32×16384+49, 32×16384+49+15680)`。

FIRST页5仍承担入口和索引存储，但它的数据不再是第一块的当前值。新代码以索引项的页号决定从FIRST的696还是DATA的49读取。

## 5. 多次更新与purge

`documents_repeated` 的id2当前FIRST已经换成85，引用版本14、长度350067；22个活动块各有13个历史项，总计286项，分配链为 `85 -> 369 -> 96 -> NULL`。活动首项在INDEX页369偏移279，指向DATA页373。

这里14次SQL更新不等于同一LOB递增14次：第一次 `CHAR()` 产生二进制opaque值，编码从350066变成350067字节，发生整值替换；后13次在新的LOB上部分更新。普通JSON视图显示 `base64:type250:...`，类型树仍保存opaque类型和原始二进制。这是实际SQL类型行为，不应偷偷改成普通文本来凑预期。

`documents_history_purged` 中相同的当前引用、活动块和列值保持不变，历史项变为0，但INDEX页369和96仍分配着。id1只有4个活动块，也仍保留INDEX页398。因此按 `ceil((活动块数−10)/272)` 要求精确分配页数会误报损坏。

同一LOB内活动版本也可能混合：id1在 `documents_holes` 中有版本2与3的块，在 `documents_reuse` 中有版本2与4的块。没有改动的块无需重写。

## 6. 当前值选择和校验边界

`lob.go` 的 `parseExternal` 解释引用，`readExternal` 执行：

1. 校验引用长度、space、实现上限和修改标志；加载FIRST并验证CRC/LSN。
2. 当前引用版本必须等于FIRST版本且非零。比FIRST新报损坏；比FIRST旧报未支持历史读取。
3. 遍历INDEX分配链，检查页类型/空间/格式/环；活动与历史项必须位于已分配的对齐槽位，同一槽不能重复出现。
4. 验证活动链的prev/next/count/尾地址；块版本应在1..当前版本。历史版本按链非递增，允许同一LOB更新中多次改同一块而出现相等版本。
5. 历史链验证地址、嵌套空表头、版本、数据页号/长度范围和端点，**不读取历史数据页**。读取当前数据页，校验重复页、长度和总字节数。
6. 拼接完整字节后，再交给字符集/JSON等解码器；不能在每页独立解码UTF-8。

事务校验有一个源码特例：`lob0update.cc:409–415` 整块替换调用 `alloc/write`，`lob0pages.cc:145–185` 不写DATA事务字段，真实中间整块页该字段为0。因此只对初始版本块保留创建事务相等检查，更新版本不施加这条不成立的约束。

`ExternalField.Reference` 保留原始20字节；`Chunks` 仍仅是当前值的有序来源，包含索引页/项偏移和数据页/偏移/长度。`Record.End` 仍只描述本地记录。

官方 `lob0impl.cc:1169–1199` 在引用较旧时会寻找不大于引用版本的历史块。本项目并未把该过程包装为历史SQL行恢复：小改旧字节可能只在undo，当前阶段又没有对应事务快照输入。版本相等也不能证明事务已提交；调用者必须提供已结束目标写事务的稳定快照。
